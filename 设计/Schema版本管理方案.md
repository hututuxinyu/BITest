# Schema管理解决方案

## 1. 概述

本文档针对报表BI系统中Schema版本管理的问题，提出了一套完整的解决方案。该方案解决了Schema版本号与网元版本的关联、多局点Schema版本管理、版本升级等关键问题。

## 2. 问题分析

### 2.1 核心问题

1. **版本号关联问题**：Schema版本号需要跟随网元版本（如27.0），但Schema的变更频率和网元版本发布频率可能不一致
2. **多局点管理问题**：不同局点可能对Schema进行定制化修改，如何管理这些局点特定的Schema版本
3. **版本升级问题**：当网元版本从27.0升级到28.0时，Schema版本号如何同步管理

### 2.2 挑战

- Schema变更可能与网元版本发布不同步
- 局点定制化Schema需要独立版本管理
- 需要支持Schema的向后兼容性
- 需要支持版本回退和迁移

## 3. 解决方案设计

### 3.1 版本号设计规范

#### 3.1.1 版本号格式

采用**四段式版本号**：`<网元主版本>.<网元次版本>.<Schema主版本>.<Schema修订版本>`

**格式说明**：
- **网元主版本**：对应网元系统的主版本号（如27）
- **网元次版本**：对应网元系统的次版本号（如0）
- **Schema主版本**：Schema结构发生不兼容变更时的版本号（从1开始）
- **Schema修订版本**：Schema的修订版本号，用于局点定制或小范围修改（从0开始）

**示例**：
- `27.0.1.0`：网元版本27.0，Schema主版本1，修订版本0（标准版本）
- `27.0.1.1`：网元版本27.0，Schema主版本1，修订版本1（局点A定制版本）
- `27.0.1.2`：网元版本27.0，Schema主版本1，修订版本2（局点B定制版本）
- `28.0.1.0`：网元版本28.0，Schema主版本1，修订版本0（升级后标准版本）

#### 3.1.2 版本号规则

1. **网元版本变更**：
   - 当网元版本从27.0升级到28.0时，Schema版本号的前两段同步更新
   - Schema主版本和修订版本根据实际变更情况决定是否递增

2. **Schema结构变更**：
   - **不兼容变更**（如删除字段、修改必填字段）：Schema主版本+1，修订版本归0
   - **兼容性新增**（如新增可选字段、新增组件类型）：Schema主版本不变，修订版本+1
   - **Bug修复**：Schema主版本不变，修订版本+1

3. **局点定制**：
   - 局点对Schema进行定制化修改时，修订版本+1
   - 每个局点的定制版本独立管理，互不影响

### 3.3 版本管理策略

#### 3.3.1 标准版本管理

**标准版本**是指由产品团队发布的、适用于所有局点的通用Schema版本。

**管理流程**：
1. **版本创建**：
   - 产品团队在设计态创建新的Schema版本
   - 系统自动生成版本号（基于当前网元版本）
   - 版本号格式：`<网元版本>.1.0`（首次创建）

2. **版本发布**：
   - 经过测试验证后，发布为标准版本
   - 存储到`standard/`目录下
   - 生成版本变更日志和迁移指南

3. **版本更新**：
   - 当Schema结构发生变更时，根据变更类型决定版本号递增规则
   - 更新版本变更日志

#### 3.3.2 局点定制版本管理

**局点定制版本**是指各局点基于标准版本进行定制化修改后的Schema版本。

**管理流程**：
1. **定制申请**：
   - 局点基于标准版本进行定制化修改
   - 系统自动生成定制版本号（修订版本+1）
   - 版本号格式：`<网元版本>.<Schema主版本>.<修订版本+1>`

2. **版本标识**：
   - 在Schema元数据中标记`versionType: "custom"`
   - 记录`siteId`和`baseVersion`（基于的标准版本）

3. **版本存储**：
   - 存储到`custom/<siteId>/`目录下
   - 保留与标准版本的关联关系

4. **版本同步**：
   - 当标准版本升级时，系统提示局点是否需要同步升级
   - 支持将定制版本的修改迁移到新版本

#### 3.3.3 版本升级管理

**场景一：网元版本升级（27.0 → 28.0）**

1. **标准版本升级**：
   - 产品团队创建新网元版本的标准Schema
   - 版本号：`28.0.1.0`（如果Schema结构未变）或`28.0.2.0`（如果Schema结构有变更）
   - 生成版本迁移指南，说明变更内容和迁移步骤

2. **局点版本升级**：
   - 系统检测到网元版本升级，通知各局点
   - 局点可以选择：
     - **直接升级**：使用新网元版本的标准Schema（`28.0.1.0`）
     - **定制升级**：基于新标准版本创建定制版本（`28.0.1.1`）
     - **保持旧版本**：继续使用旧版本（需要评估兼容性）

3. **兼容性处理**：
   - 运行态系统支持多版本Schema解析
   - 提供版本适配器，将旧版本Schema转换为新版本格式
   - 支持渐进式升级，允许部分报表使用新版本，部分使用旧版本

**场景二：Schema结构升级（27.0.1.0 → 27.0.2.0）**

1. **不兼容变更处理**：
   - Schema主版本+1，修订版本归0
   - 生成详细的变更日志和迁移脚本
   - 提供自动迁移工具，将旧版本Schema转换为新版本

2. **兼容性变更处理**：
   - 修订版本+1
   - 新版本兼容旧版本，运行态系统同时支持两个版本
   - 逐步迁移到新版本

### 3.4 版本兼容性处理

#### 3.4.1 运行态版本适配

运行态系统需要支持多版本Schema的解析和渲染：

```typescript
interface SchemaAdapter {
  // 检查Schema版本是否支持
  isVersionSupported(version: string): boolean;
  
  // 将旧版本Schema转换为当前版本
  migrateSchema(oldSchema: ReportSchema, targetVersion: string): ReportSchema;
  
  // 解析Schema（自动处理版本兼容）
  parseSchema(schema: ReportSchema): ParsedReport;
}
```

#### 3.4.2 版本兼容性矩阵

维护版本兼容性矩阵，明确哪些版本之间可以兼容：

| 网元版本 | Schema主版本 | 是否兼容 | 说明 |
|---------|-------------|---------|------|
| 27.0    | 1.x         | 是      | 同一主版本下的修订版本互相兼容 |
| 27.0    | 2.x         | 否      | 主版本变更，需要迁移 |
| 28.0    | 1.x         | 部分    | 需要评估网元版本变更的影响 |

### 3.5 版本查询和检索

#### 3.5.1 Schema版本服务

提供Schema版本管理服务，支持：

1. **版本查询**：
   - 根据报表ID查询所有版本
   - 根据网元版本查询标准版本列表
   - 根据局点ID查询定制版本列表

2. **版本比较**：
   - 比较两个版本之间的差异
   - 生成变更报告

3. **版本推荐**：
   - 根据网元版本推荐合适的Schema版本
   - 检测过时版本并提示升级

#### 3.5.2 API接口设计

```typescript
// Schema版本管理API
interface SchemaVersionService {
  // 获取报表的所有版本
  getReportVersions(reportId: string): Promise<VersionInfo[]>;
  
  // 获取指定版本的Schema
  getSchemaByVersion(reportId: string, version: string): Promise<ReportSchema>;
  
  // 获取标准版本列表
  getStandardVersions(networkElementVersion: string): Promise<VersionInfo[]>;
  
  // 获取局点定制版本
  getCustomVersions(siteId: string, networkElementVersion: string): Promise<VersionInfo[]>;
  
  // 创建新版本
  createVersion(baseVersion: string, changes: SchemaChanges): Promise<VersionInfo>;
  
  // 版本迁移
  migrateVersion(sourceVersion: string, targetVersion: string): Promise<MigrationResult>;
}
```

### 3.6 版本迁移策略

#### 3.6.1 自动迁移

对于兼容性变更，提供自动迁移工具：

1. **字段映射**：自动映射旧版本字段到新版本字段
2. **默认值填充**：为新版本新增的必填字段填充默认值
3. **结构转换**：自动转换结构变更（如字段重命名、类型转换）

#### 3.6.2 手动迁移

对于不兼容变更，提供迁移指南和工具：

1. **迁移脚本**：提供迁移脚本模板
2. **迁移检查**：检查Schema是否可以自动迁移
3. **迁移验证**：验证迁移后的Schema是否正确

#### 3.6.3 迁移流程

```
1. 分析版本差异
   ↓
2. 生成迁移计划
   ↓
3. 执行自动迁移（如可能）
   ↓
4. 手动处理不兼容变更
   ↓
5. 验证迁移结果
   ↓
6. 更新版本信息
```

## 5. 最佳实践

### 5.1 版本命名规范

1. **遵循版本号格式**：严格按照四段式版本号格式
2. **版本号唯一性**：确保每个版本号全局唯一
3. **版本号递增**：版本号只能递增，不能回退

### 5.2 变更管理

1. **变更记录**：所有Schema变更都要记录在变更日志中
2. **变更影响分析**：评估变更对现有报表的影响
3. **向后兼容**：尽量保持向后兼容，减少迁移成本

### 5.3 局点定制

1. **最小化定制**：尽量使用标准版本，减少定制
2. **定制文档化**：详细记录定制内容和原因
3. **定期同步**：定期评估是否需要同步标准版本的新特性

### 5.4 版本升级

1. **升级计划**：制定详细的版本升级计划
2. **测试验证**：升级前充分测试
3. **回滚准备**：准备版本回滚方案

## 6. 监控和运维

### 6.1 版本使用监控

1. **版本分布统计**：统计各版本的使用情况
2. **过时版本检测**：检测并提示过时版本
3. **版本兼容性监控**：监控版本兼容性问题

### 6.2 版本管理工具

1. **版本管理界面**：提供可视化的版本管理界面
2. **版本比较工具**：提供版本差异比较工具
3. **迁移工具**：提供版本迁移工具和脚本

## 7. 总结

本方案通过四段式版本号设计、标准版本和局点定制版本分离管理、版本兼容性处理等机制，解决了Schema版本管理的核心问题。该方案具有以下优势：

1. **清晰的版本标识**：通过四段式版本号，清晰标识Schema的版本信息
2. **灵活的定制支持**：支持局点定制版本，同时保持与标准版本的关联
3. **平滑的版本升级**：通过兼容性处理和迁移工具，支持平滑的版本升级
4. **完善的版本管理**：提供完整的版本查询、比较、迁移等功能

通过实施本方案，可以有效解决Schema版本管理中的各种问题，确保系统的稳定性和可维护性。
